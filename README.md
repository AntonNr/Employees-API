# API сотрудников

REST API для управления сотрудниками, их зарплатами и отделами. Позволяет создавать, редактировать, удалять и просматривать записи (одну или списком).

**Стек:** Python, Django, Django REST Framework, PostgreSQL, python-dotenv.

Требуется Python 3.12 или новее (проект разрабатывался на Python 3.15).

## Сущности

### Сотрудник (`employees`)

| Поле | Описание |
|---|---|
| `id` | Идентификатор (только чтение) |
| `first_name` | Имя |
| `second_name` | Фамилия |
| `age` | Возраст в годах (не меньше 14) |
| `departments` | Список `id` отделов из справочника, например `[1, 2]`. Может быть пустым |
| `create_date` | Дата создания записи (только чтение). Значение по умолчанию ставит сама база данных (`DEFAULT now()`) |

### Зарплата сотрудника (`salaries`)

У сотрудника может быть только одна запись о зарплате (связь «один к одному»).

| Поле | Описание |
|---|---|
| `id` | Идентификатор (только чтение) |
| `employee` | `id` сотрудника |
| `salary` | Зарплата в BYN, до двух знаков после запятой (не меньше 0) |

### Отдел (`departments`)

Отделы — отдельный справочник: каждый отдел хранится один раз и не ссылается на сотрудников. Сотрудник и отделы связаны отношением «многие ко многим»: у сотрудника может быть несколько отделов, в отделе — несколько сотрудников.

| Поле | Описание |
|---|---|
| `id` | Идентификатор (только чтение) |
| `name` | Название отдела (уникальное, с учётом регистра: `IT` и `it` — разные отделы) |

## Запуск проекта

### 1. Подготовка

- Установленные Python 3.12+ и PostgreSQL.
- Клонированный репозиторий, команды ниже выполняются в его корневой папке.

### 2. Виртуальное окружение и зависимости

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

В Windows окружение активируется командой `venv\Scripts\activate`.

### 3. База данных

1. В PostgreSQL создайте пустую базу данных, например `employees_db` (через pgAdmin или командой `createdb employees_db`).
2. Запомните её имя, пользователя, пароль, хост и порт: они понадобятся на следующем шаге.

### 4. Переменные окружения

1. Скопируйте файл `.env.example` в `.env`:

```bash
cp .env.example .env
```

2. Заполните в `.env` переменные, у которых нет значения:

| Переменная | Описание | Значение в `.env.example` |
|---|---|---|
| `DJANGO_SECRET_KEY` | Секретный ключ Django | **нужно заполнить** (команда ниже) |
| `DJANGO_DEBUG` | Режим отладки | `True` (подходит для локального запуска) |
| `DB_NAME` | Имя базы данных | **нужно заполнить**, например `employees_db` |
| `DB_USER` | Пользователь PostgreSQL | **нужно заполнить**, например `postgres` |
| `DB_PASSWORD` | Пароль пользователя | **нужно заполнить** |
| `DB_HOST` | Хост PostgreSQL | `127.0.0.1` |
| `DB_PORT` | Порт PostgreSQL | `5432` |

3. Секретный ключ можно сгенерировать командой:

```bash
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

Вставьте полученную строку в `.env` внутри одинарных кавычек: `DJANGO_SECRET_KEY='...'`. В ключе бывают символы `#`, `$`, `%`, и кавычки защищают их от неверного разбора.

Важно:

- **Пустое значение считается ошибкой.** Если оставить, например, `DB_NAME=` пустым, Django сообщит, какую переменную нужно заполнить. Если строки переменной нет в `.env` совсем, для `DJANGO_DEBUG`, `DB_HOST` и `DB_PORT` используются значения по умолчанию (`False`, `127.0.0.1`, `5432`), остальные переменные обязательны.
- Для локального запуска оставьте `DJANGO_DEBUG=True`. При `False` Django требует заполненный `ALLOWED_HOSTS`, а в проекте он не задан.
- Файл `.env` читается автоматически при запуске любой команды `manage.py`, экспортировать переменные вручную не нужно. Если та же переменная уже задана в окружении терминала, она приоритетнее значения из файла.
- Файл читается один раз при старте. После изменения `.env` остановите сервер (`Ctrl+C`) и запустите его заново.
- Файл `.env` не попадает в репозиторий (он указан в `.gitignore`).

### 5. Миграции

```bash
python manage.py migrate
```

Время хранится в базе в UTC, отображается по Минску (`Europe/Minsk`).

### 6. Запуск сервера

```bash
python manage.py runserver
```

API будет доступен по адресу `http://127.0.0.1:8000/api/`. Страница корня показывает ссылки на все три эндпоинта, и через неё же можно пробовать запросы прямо в браузере (встроенный интерфейс DRF).

## Эндпоинты

Для каждой сущности доступны одинаковые операции:

| Метод | Адрес | Действие |
|---|---|---|
| `GET` | `/api/<сущность>/` | Список (с пагинацией) |
| `POST` | `/api/<сущность>/` | Создание |
| `GET` | `/api/<сущность>/<id>/` | Просмотр одного элемента |
| `PUT` | `/api/<сущность>/<id>/` | Полное изменение (нужно передать все поля) |
| `PATCH` | `/api/<сущность>/<id>/` | Частичное изменение (только изменяемые поля) |
| `DELETE` | `/api/<сущность>/<id>/` | Удаление |

Где `<сущность>`: `employees`, `salaries` или `departments`.

### Отделы сотрудника одной строкой

| Метод | Адрес | Действие |
|---|---|---|
| `GET` | `/api/employees/<id>/departments/` | Все отделы сотрудника одной строкой |

Пример ответа:

```json
{"departments": "IT, RDI"}
```

- Названия отсортированы по алфавиту и разделены запятой с пробелом.
- Если у сотрудника нет отделов, приходит пустая строка.
- Если сотрудника нет, ответ `404`.
- Строку собирает PostgreSQL (`string_agg`) — сотрудник и его отделы получаются одним SQL-запросом.

Назначить сотруднику отделы можно при создании (`POST`) или изменении (`PUT`/`PATCH`) сотрудника, передав список `id` отделов:

```json
{"departments": [1, 2]}
```

## Проверка данных

- `age` не меньше 14.
- `salary` не отрицательная, не более двух знаков после запятой.
- Имя и фамилия не могут быть пустыми, не могут состоять только из цифр и должны содержать хотя бы одну букву (не длиннее 100 символов).
- Название отдела не может быть пустым и должно быть уникальным.
- У сотрудника может быть только одна запись о зарплате.
- Отделы сотрудника необязательны: сотрудника можно создать без отделов. Передать несуществующий `id` отдела нельзя.
- `id` и `create_date` задаются сервером: если передать их в запросе, они будут проигнорированы.
